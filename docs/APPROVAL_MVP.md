# 承認＋連絡先 MVP（開発ブランチ限定）

## 判断ログ

- 判断：凍結版 `fdc26b2` を基点とする `approval-contact-mvp` だけに追加する。Production は反映しない。
- 理由：仕入れ案の提示から「双方が直接相談へ進める」瞬間までをデモで証明する。
- 捨てた案：本格チャット、注文、決済、在庫予約、配送手配、通知配信。
- トレードオフ：承認しても商品は確保されない。最終的な数量・日程・注文は当事者間で相談する。
- 審査上の意味：飲食店の次の行動と、生産者が条件を見て応答する理由を一つの流れで示せる。

### 取引の流れ（Issue E・2026-10-20）

- 判断：同じ仕入れ案（planFingerprint）の全農家が「対応できます」になった時点で取引を成立とし、以降は仕入れ案を計算し直さない（stale にしない）。保存済みの品目・数量・価格・小計・受け取り場所・日時を、合意した内容として扱う。成立前（返事待ち・一部だけ承諾）は従来どおり計算し直して stale を判定する。fingerprint の作り方は変えない。
- 理由：成立後に生産者が残りの量や価格を変えるのは自然な操作で、そのたびに取引・連絡先・やり取りが消えるのは不自然。
- 判断：受け取り完了は仕入れ案ごとに飲食店が1回押し、同じ仕入れ案の「対応できます」の行すべてに同じ receivedAt を1つのトランザクションで入れる（何度押しても同じ結果）。受け取り完了＝取引完了とする（評価・決済はない）。
- 判断：MVP では、取引が成立していれば予定の受け取り日時より前でも「受け取り完了」を押せる（早めの受け渡しも許す）。将来は受け取り時刻の制御、キャンセル、受け取り後の取り消しなどを含めて制御する余地がある。
- 判断：やり取りは相談1件（飲食店×生産者×仕入れ案）に紐づくテキストだけ（trade_messages）。読み書きはその飲食店と生産者だけ、取引の成立後だけ。15秒ごとの読み直しと「更新」ボタンで取得する。
- 捨てた案：WebSocket、既読、画像、削除、入力中表示、評価、AI 返信、高度な通知、1農家が辞退したときの自動の組み直し（「仕入れ案を作り直してください」と案内するだけ）。

## 接続と安全装置

- `.env.local` は変更しない。秘密値は Git・ログ・画面に出さない。
- ローカルの起動、DB操作スクリプト、Prisma の DB操作は `.env.approval.local` を明示的に読み込む。ファイル不在時は停止し、本番設定へ戻らない。
- `server/db-safety.ts` は Neon main と mvp-redesign の endpoint を拒否する。approval-dev の endpoint、データベース名、pooled/directの一致を必須とする。
- Prisma の CLI 設定にも同じガードを置くため、package.json を通さない通常の Prisma コマンドも対象。`generate`/`validate`/`format`/`version` はDB接続を伴わないため除外。
- Vercel 上の DB操作は許可しない。ローカルのビルドはデプロイではない。
- ガードはこのブランチの標準操作経路を保護するもの。別の設定ファイルや独立したSQLクライアントまでシステム全体で禁止するものではない。

## 保存する承認対象

`restaurantId + supplyId + planFingerprint` を unique とする。
fingerprint は正規化した希望条件、既存の在庫版、各割当の数量・価格・供給version、受取枠のスナップショットからサーバーで SHA-256 を生成する。計算時刻は含めない。

依頼を作る際にサーバーで再計算し、画面の版と fingerprint が一致し、条件を満たす案（MATCHED）で締切前の場合だけ保存する。クライアント指定の生産者・数量・単価は採用しない。同一内容の再送は既存依頼を返す。条件変更後は別依頼とし、旧依頼を上書きしない。

回答・一覧・連絡先取得でも現在の条件と照合する。供給・枠・参加・店の取引経験など既存versionの対象が変わった場合は「再確認が必要」とし、古い承認で連絡先を取得できない。締切後も同様。判定は安全側に寄せ、同じ品目の候補在庫が変わっても失効することがある。

作成・回答・連絡先取得はトランザクションで行う。承認による供給更新は行わない。serializable競合は限定回数リトライする。

## 連絡先と画面

- Producer に任意の電話・メールのみを追加。連絡先なしでの承認は拒否し、本人が登録する。
- 依頼一覧、計算結果、catalog、me には連絡先を含めない。
- 連絡先の取得は依頼者本人・承認済・現在も有効の場合のみ。生産者は自分のプロフィールだけ登録・更新できる。
- 画面は15秒ごととフォーカス復帰時に確認状態を更新する。通信エラー時は以前の承認・連絡先を有効表示しない。連絡先はブラウザ保存領域へ保存しない。
- `GET/POST /api/approvals`：本人の一覧/依頼作成。`GET ?view=contact` / `PATCH`：本人の連絡先。
- `GET /api/approvals/:id`：承認後の連絡先。`PATCH`：生産者の回答。
- 確認依頼は最新100件まで表示。大量履歴の運用は今回の範囲外。
- 開示済みの連絡先を相手の記憶や外部への保存から取り消すことはできない。

## デモ

1. 飲食店で10kgを複数農園から組む案を作り、「生産者に確認する」を押す。
2. 各農園で数量・金額・日時・場所を確認する。デモ生産者は初期状態で架空の連絡先が登録済みのため、準備操作なしで承認できる。
3. 一方だけ承認→飲食店は「確認中」、承認農園だけ連絡先を表示。
4. 全員承認→「全員承認済」。NGを含む場合は「一部NG」。
5. 在庫を更新→旧承認が失効。再計算した案は新しい確認対象になる。

デモ生産者の連絡先は A〜D 農園とも初期状態で登録済み（電話 `000-0000-0001`〜`0004`、メール `a-farm@example.invalid` 〜 `d-farm@example.invalid`。明らかに架空の値）。reset-demo で毎回この値に戻る。実際の送信・発信はしない。reset-demo は approval-dev に限定され、確認依頼も消して初期化する。

## 検証結果

- 既存分を含む134件のテストが成功。型チェックと本番用ビルドも成功（デプロイは実施していない）。
- `scripts/verify-approval.ts` で独立した `approval-check-*` データを作り、実HTTPログイン、同時再送の重複防止、本人以外の拒否、承認前の拒否、承認/NG/全員承認、連絡先取得、在庫不変、在庫更新後の失効、再計算後の再確認を実DBまで検証した。
- ブラウザでも飲食店の条件入力・案の計算・依頼送信、生産者の承認、飲食店で承認済み農園のみ連絡先が表示されることを確認した。
- 390px幅で横はみ出しがないことと、既存の数量更新画面が残ることを確認した。
- 一連の検証はローカルアプリと approval-dev のみを使用。Productionへは反映していない。
